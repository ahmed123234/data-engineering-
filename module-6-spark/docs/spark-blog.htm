The Context

Week 6 of the Data Engineering Zoomcamp

After five weeks of databases, pipelines, and cloud infrastructure, week six threw us into the deep end of distributed computing. The assignment: install Apache Spark from scratch, ingest November 2025's entire Yellow Taxi dataset, and answer six analytical questions — all using PySpark DataFrames.

What sounds simple on paper turns out to be a genuinely satisfying exercise in how distributed engines think differently from single-machine pandas workflows. Lazy evaluation, partitioning strategies, query planning — Spark exposes all of it, and this homework made each concept concrete.

Spark doesn't run your code. It builds a plan, optimises it, then runs it. That distinction changes how you write every line.

This post walks through the full solution: what the questions asked, what the code looks like, and what I learned from each one. The complete repo is open — clone, run, explore.

The Code

Walking Through the Key Patterns

Creating the Spark Session

Every PySpark script starts here. local[*] tells Spark to use all available CPU cores on the local machine — no cluster needed.

Python 
from pyspark.sql import SparkSession

spark = SparkSession.builder \
    .master("local[*]") \
    .appName("de-zoomcamp-hw6") \
    .config("spark.sql.shuffle.partitions", "4") \
    .getOrCreate()

# Q1 — version
print(spark.version)  # → 3.5.3

Repartitioning and Measuring File Sizes

The key insight: repartition shuffles data across N evenly-sized partitions. Writing to Parquet produces one file per partition. Measuring the files after the write gives us the real compressed size — not an estimate.

Python 
df = spark.read.parquet("data/yellow_tripdata_2025-11.parquet")

df.repartition(4) \
  .write.mode("overwrite") \
  .parquet("output/yellow_2025_11_repartitioned")

# Measure each .parquet file
files    = [f for f in os.listdir(OUTPUT_DIR) if f.endswith(".parquet")]
sizes_mb = [os.path.getsize(f"{OUTPUT_DIR}/{f}") / (1024 ** 2) for f in files]
avg_mb   = sum(sizes_mb) / len(sizes_mb)
print(f"Average: {avg_mb:.2f} MB")  # → ~25 MB

Counting Trips and Finding the Longest

Spark's filter() pushes predicates into the scan — it doesn't load then filter, it avoids reading irrelevant row groups entirely when working with Parquet. The duration calculation uses unix_timestamp to diff two datetime columns in seconds, then divides by 3600.

Python 
from pyspark.sql.functions import col, to_date, unix_timestamp, max as spark_max

# Q3 — trips on Nov 15
count = df.filter(to_date(col("tpep_pickup_datetime")) == "2025-11-15").count()
print(count)  # → 62,610

# Q4 — longest trip
df_dur = df.withColumn(
    "hours",
    (unix_timestamp("tpep_dropoff_datetime") -
     unix_timestamp("tpep_pickup_datetime")) / 3600.0
)
max_h = df_dur.select(spark_max("hours")).collect()[0][0]
print(f"{max_h:.1f} hours")  # → 90.6 hours

Zone Join with Spark SQL

The final question combines two datasets — trips and zone lookups — using Spark SQL. Creating temp views lets us write plain SQL against DataFrames, which is often cleaner for aggregation + join patterns.

Python + Spark SQL 
zones = spark.read.option("header", "true").csv("data/taxi_zone_lookup.csv")

df.createOrReplaceTempView("trips")
zones.createOrReplaceTempView("zones")

result = spark.sql("""
    SELECT z.Zone, COUNT(*) AS pickup_count
    FROM   trips t
    JOIN   zones z
      ON   CAST(t.PULocationID AS INT) = CAST(z.LocationID AS INT)
    GROUP  BY z.Zone
    ORDER  BY pickup_count ASC
    LIMIT  10
""")

result.show(truncate=False)
# → Governor's Island/Ellis Island/Liberty Island

Takeaways

What This Week Actually Taught Me

Going in, I understood Spark conceptually. Coming out, I understand it operationally. There's a gap between "Spark uses lazy evaluation" and watching the Spark UI show you a zero-task stage because the optimizer eliminated it entirely.

The repartitioning question was the most revealing. A single repartition(4) triggers a full shuffle — every row moves across the cluster. That's expensive. In production you'd use coalesce() when reducing partitions and only reach for repartition() when you need balanced, parallelism-optimised output files.

The zone join question illustrated why schema discipline matters. PULocationID is stored as a long integer in the Parquet file but LocationID comes in as a string from the CSV — the explicit CAST in the SQL prevents a silent cross-join that would return nothing.

The Spark UI at port 4040 is not optional reading. It's where you learn why your job is slow, and where the optimizer surprises you by being smarter than you expected.
